# Утренний велобот по Ярославлю

Telegram-бот, который каждое утро (по команде или через день по расписанию)
подбирает **один** безопасный утренний кольцевой веломаршрут с Волковской
площади в Ярославле — с учётом реального прогноза погоды и одной проверенной
столовой рядом с маршрутом.

Вся логика выбора погоды, маршрута и столовой — обычный Python-код без
использования LLM/AI API. Улицы, расстояния, погодные показатели и заведения
берутся только из ответов Open-Meteo, OpenRouteService и CSV-файла — ничего
не выдумывается.

## Технологии

- Python 3.12, aiogram 3, httpx, APScheduler, python-dotenv, pytest
- Open-Meteo Forecast API (почасовая погода)
- OpenRouteService Directions API, профиль `cycling-regular`, `round_trip`
- Часовой пояс: `Europe/Moscow`

## Архитектура

```
bot.py               — запуск бота, обработчики /start и /route, оркестрация
config.py            — все настройки и константы
services/weather.py  — Open-Meteo: прогноз, выбор безопасного утреннего окна
services/routes.py   — OpenRouteService: построение кольцевого маршрута
services/food.py     — чтение CSV, поиск заведения рядом с маршрутом
services/message.py  — форматирование сообщения в Telegram
scheduler.py         — рассылка через день в заданное время
storage.py           — история маршрутов и дата последней рассылки (JSON)
tests/               — pytest для ключевой логики (без сети и без Telegram)
food_places.csv      — база проверенных заведений (см. схему ниже)
data/                — создаётся автоматически: storage.json, last_route.geojson
```

## Решения по неоднозначным местам ТЗ

Зафиксировано явно, как и просили, чтобы не гадать при реализации:

1. **Имя CSV-файла.** В ТЗ упомянуты два имени: `food_places.csv` (раздел
   «Архитектура») и `gde_poest_tolko_vashi_mesta_for_make(2).csv» (раздел
   «Работа со столовыми»). Взято `food_places.csv` как рабочее имя, путь
   настраивается константой `config.FOOD_CSV_PATH`. Если ваш реальный файл
   называется иначе — либо переименуйте его в `food_places.csv`, либо
   поменяйте `FOOD_CSV_PATH` в `config.py`. Формат колонок — ниже.
2. **Точки старта/финиша.** В `config.py` (`START_POINTS`) заданы несколько
   точек в центре Ярославля (Волковская площадь, Волжская набережная,
   Богоявленская площадь, Красная площадь, Октябрьская площадь, КЗЦ
   «Миллениум»). Все координаты приблизительные, по открытым картографическим
   данным — перед боевым использованием проверьте каждую (например, через
   Яндекс.Карты: ПКМ по точке → «Что здесь?») и при необходимости
   скорректируйте прямо в `config.py`.

   По командам `/start` и `/route` бот сначала показывает inline-кнопки с
   этими точками и кнопку «📍 Произвольный старт». При выборе последней бот
   просит прислать геолокацию (Telegram: 📎 → «Локация», либо кнопка
   «Отправить геолокацию» на клавиатуре) и строит маршрут от неё — без
   геокодинга адресов, точка берётся напрямую из координат, которые Telegram
   отдаёт при отправке геолокации. Если присланная точка дальше
   `config.MAX_CUSTOM_START_DISTANCE_FROM_CENTER_M` (15 км) от центра города,
   бот вежливо отказывает: погода всё равно считается для центра Ярославля
   (см. ниже), и маршрут от далёкой точки был бы недостоверным.

   После точки старта бот показывает вторую клавиатуру — выбор дня среди
   ближайших трёх (`services/weather.evaluate_all_days` оценивает каждый день
   отдельно). Дни без безопасного окна помечены ⚠️ и при нажатии просто
   объясняют причину (гроза, сильный дождь и т.д.), не строя маршрут — как и
   требует ТЗ. Есть и кнопка «🎲 Пусть бот выберет лучший день» — тогда
   выбор происходит автоматически, как раньше. Для рассылки по расписанию
   (без пользователя) день тоже выбирается автоматически.

   Для автоматической рассылки по расписанию (без участия пользователя)
   точка выбирается автоматически через `services/routes.choose_start_point`
   — по возможности не повторяя точку из прошлого раза, чтобы маршруты
   получались разнообразнее.
3. **Длительность утреннего окна 90–150 минут.** Open-Meteo hourly отдаёт
   данные только на границах часа, без интерполяции (интерполяцию явно
   запрещено придумывать). Поэтому единственное окно, которое физически
   попадает в диапазон 90–150 минут и укладывается в 07:00–09:30, — это блок
   **07:00–09:00 (120 минут)**. Алгоритм общий (перебирает все возможные
   комбинации часовых индексов), но на практике с часовой сеткой Open-Meteo
   всегда сойдётся к этому блоку.
4. **Целевая длина маршрута под доступное время.** Взято допущение о средней
   скорости спокойной велопрогулки — `config.ASSUMED_CYCLING_SPEED_KMH = 16`
   км/ч. Это оценка для планирования целевой длины запроса к ORS, а не
   выдуманное значение расстояния/времени в итоговом сообщении — реальные
   дистанция и время всегда берутся из ответа OpenRouteService.
5. **Порог «сильный дождь».** Использован стандартный метеорологический
   порог интенсивности осадков **> 7.6 мм/ч** (классификация, близкая к
   Met Office / NWS).
6. **Ссылка на маршрут.** Готового бесплатного способа получить ссылку с
   полной геометрией маршрута нет, поэтому бот выдаёт ссылку на **точку
   старта** на Яндекс.Картах и отдельно текстовые улицы/шаги маршрута,
   полученные из ORS. Ссылка явно подписана как «точка на карте», а не как
   готовый маршрут.
7. **«Через день».** Планировщик проверяет расписание ежедневно в
   `SEND_HOUR:SEND_MINUTE`, но реально отправляет только если с прошлой
   рассылки прошло не менее `config.SEND_INTERVAL_DAYS = 2` календарных дней
   (дата хранится в `data/storage.json`).
8. **Предполагаемое время заезда в столовую (запасной сценарий).** Если
   маршрут не удалось проложить именно через столовую (см. пункт 9), а
   подходящее заведение просто оказалось в радиусе 700 м от обычного
   round_trip-маршрута, временем заезда считается расчётное время
   **возвращения** (старт + длительность маршрута по данным ORS).
9. **Маршрут через столовую.** Перед обычным случайным round_trip бот
   пытается построить маршрут по трём точкам «старт → заведение → тот же
   старт» (`services/routes.build_route_via_waypoint`) — так ORS прокладывает
   реальный путь именно через одно из открытых проверенных заведений в
   пределах `config.MAX_FOOD_WAYPOINT_DISTANCE_M` (4 км, но не больше
   половины целевой длины маршрута) от точки старта. Время прибытия к
   заведению берётся из фактической длительности первого отрезка маршрута
   (ответ ORS), а не из приблизительной оценки. Если ни один кандидат не
   подошёл (нет координат, всё закрыто, маршрут не укладывается в лимиты
   времени/дистанции) — бот строит обычный round_trip и ищет заведение рядом
   с ним постфактум (пункт 8), как раньше.

## Схема `food_places.csv`

Формат подстроен под реальный файл пользователя: разделитель `;`, поля в
кавычках, кодировка UTF-8. Одна строка — одно заведение.

| Колонка | Описание |
|---|---|
| Название | Точное название |
| Тип | Свободный текст, не используется в логике |
| Адрес | Точный адрес — выводится в сообщении как есть |
| Район / ориентир | Свободный текст, не используется в логике |
| Дни работы | Только `ежедневно` или `пн–пт` распознаются кодом как график; любое другое значение (например «уточнить», «не рекомендовать без проверки») — заведение автоматически считается неподтверждённым |
| Открытие / Закрытие | Время в формате `HH:MM`; `не указано`/`уточнить` — заведение неподтверждено. Закрытие раньше открытия (например `07:00`–`00:00`) понимается как график через полночь |
| Подходит утром 07:30–09:30 | Не используется кодом (пересчитывается заново из Открытие/Закрытие/Дни работы, чтобы не полагаться на текст, который может устареть) |
| Ссылка на Яндекс Карты | Выводится в сообщении как есть |
| Статус проверки | Не используется кодом (свободный текст) |
| Проверено | Дата последней проверки; пустое значение = заведение неподтверждено |
| Комментарий для AI | **Намеренно не читается кодом.** Бот не использует ИИ во время работы, поэтому любые текстовые инструкции/уточнения в этой колонке игнорируются — решение принимается только по структурным полям выше |
| latitude / longitude | Широта/долгота заведения. **Обязательны** для попадания в выдачу: без них невозможно честно проверить правило «не дальше 700 м от маршрута», и заведение не будет предложено, даже если остальные поля в порядке |

Файл `food_places.csv` в проекте — это ваши реальные данные с добавленными
пустыми колонками `latitude`/`longitude`. Пока координаты не заполнены, бот
для любого маршрута отвечает «Открытой столовой рядом с маршрутом в это время
нет» — это ожидаемо и честно, а не баг.

## Настройка `.env`

Скопируйте `.env.example` в `.env` и заполните:

```
TELEGRAM_BOT_TOKEN=токен от @BotFather
OPENROUTESERVICE_API_KEY=ключ с openrouteservice.org (бесплатный тариф подходит)
TELEGRAM_CHAT_ID=id чата/канала для автоматической рассылки
SEND_HOUR=15
SEND_MINUTE=0
```

`.env` уже в `.gitignore` — никогда не коммитьте реальные ключи. В логах и в
исходном коде ключи не сохраняются: HTTP-заголовки с ключами не логируются,
в случае ошибок внешних API в лог пишется только техническое сообщение без
секретов, а пользователю — короткий понятный текст.

## Запуск (Windows PowerShell)

```powershell
# Создать и активировать виртуальное окружение
python -m venv .venv
.\.venv\Scripts\Activate.ps1

# Установить зависимости
pip install -r requirements.txt

# Заполнить .env и food_places.csv (см. выше)
copy .env.example .env

# Прогнать тесты
pytest

# Запустить бота (бесконечный процесс — запускайте осознанно)
python bot.py
```

Для остановки бота — `Ctrl+C` в том же окне PowerShell.

## Постоянная работа (деплой на Railway/Render)

GitHub сам по себе код не выполняет — это только хранилище. Чтобы бот работал
круглосуточно, репозиторий подключается к PaaS-хостингу (Railway или Render),
который его реально запускает и передеплоивает при каждом `git push`.

В репозитории уже есть нужные файлы:
- `Procfile` — команда запуска: `worker: python bot.py` (это фоновый воркер,
  не веб-сервис — у бота нет HTTP-порта, он сам ходит в Telegram по polling).
- `runtime.txt` — версия Python (3.12.10).

Шаги (одинаковые для Railway и Render):
1. Зарегистрируйтесь и подключите свой GitHub-аккаунт в панели сервиса.
2. Создайте новый проект/сервис из этого репозитория.
3. Выберите тип **Worker / Background Worker** (не Web Service).
4. В настройках окружения (Environment Variables) добавьте вручную:
   `TELEGRAM_BOT_TOKEN`, `OPENROUTESERVICE_API_KEY`, `TELEGRAM_CHAT_ID`,
   `SEND_HOUR`, `SEND_MINUTE` — то же самое, что в вашем `.env` (сам `.env`
   в репозиторий не попадает, это сделано намеренно).
5. Запустите деплой. После этого при каждом `git push` в основную ветку
   сервис автоматически подтянет новый код и перезапустит бота.

**Важная особенность бесплатных тарифов:** диск на них обычно не сохраняется
между деплоями (ephemeral filesystem). Это значит, что при каждом передеплое
`data/storage.json` (история маршрутов и дата последней рассылки) обнулится.
Практическое следствие: сразу после деплоя бот может посчитать, что рассылки
никогда не было, и прислать маршрут при ближайшей проверке расписания, а
защита «не повторять один и тот же маршрут два раза подряд» на время
сбрасывается. Для личного бота это не критично, но полезно знать. Если это
станет мешать — на Railway можно подключить постоянный Volume под `data/`
(в бесплатном плане может быть недоступно).

## Тесты

`pytest` покрывает только детерминированную логику (без сетевых вызовов и без
Telegram): разбор и оценку прогноза погоды, валидацию и сравнение маршрутов,
чтение CSV и поиск заведения рядом с маршрутом, форматирование сообщения и
логику «через день» в планировщике.
